## 1. 目标与已确认需求

本仓库用于逐步开发多个小工具，主要通过 CLI 使用，支持 macOS、Linux 和 Windows。第一个工具提供图片压缩与格式转换，PNG 是重点优化对象。用户希望在保证图片质量的情况下尽量减少文件字节数，并以超过现有开源 PNG 工具的压缩效果为研发目标。

用户已澄清“矢量”为笔误，实际要求是保证图片质量。用户尚未指定编程语言、具体格式清单、压缩耗时上限或发布方式。

以下标记为“建议”的内容是本次设计选择，并非用户已经确认的决定。用户确认本文后，再编写实施计划并开始开发。遵守仓库约定：中文文档、关键流程有中文注释，未经用户明确确认不执行 git commit。

## 2. 建议的质量标准

### PNG 压缩：默认严格无损

- 输出仍为标准 PNG，尺寸不变；按原始精度解码并展开调色板后，每个像素的颜色和 Alpha 与输入一致。
- 保留 16-bit 原图的精度；不通过统一转为 RGBA8 来验证无损。
- 保留完全透明像素中隐藏的 RGB；默认关闭透明区改色、颜色量化和有损降位深。
- 保留影响显示的颜色空间、ICC、gamma、方向以及相关 HDR 信息。只比较像素数组不足以证明显示效果不变。
- 元数据默认保留。可能使已有元数据失效的编码变换，仅在能维持其语义时采用；未知或不能可靠处理的情况放弃该候选。保留原文件是合法结果。
- 提供显式的元数据清理选项，仅移除明确不影响显示的已知信息；其节省量单独报告，不算作压缩算法优势。
- 先验证候选，再比较字节数；没有更小且合格的候选时，输出原文件内容。

“像素级无损”是当前建议的默认底线。首版不引入颜色量化的视觉有损模式；若后续需要类似 pngquant 的效果，单独提供明确标注的模式和质量指标。

### 格式转换：按目标格式能力处理

压缩和转换是不同操作。转换到 JPEG、GIF 等受限目标时，可能无法保留任意原图的颜色、透明度或其他信息；不能把所有转换都称为无损。

默认拒绝会丢失颜色精度、透明度、动画帧、图层或页数的转换，并说明具体原因。用户通过明确选项选择质量、背景色、帧、页或合成图后，才执行相应转换；不得静默取第一帧或丢弃透明度。JPEG 等有损目标要求显式选择允许有损及质量参数。

## 3. “全格式”对应的可实现范围

目标是广泛覆盖图片格式，并显示真实的读写能力。读某格式和写某格式是不同能力；位图转换为 SVG 也不能自动恢复原始矢量路径。因此使用输入／输出能力矩阵，不声明无限制的全格式无损互转。

建议首个交付版本覆盖：

| 范围 | 首版行为 |
| --- | --- |
| 静态 PNG | 内置无损压缩、信息检查、输出验证，是核心验收对象 |
| JPEG、WebP、BMP、TIFF、GIF、ICO、AVIF 的静态图片 | 经转换后端读取和写入；是否可保真转换取决于源内容和目标能力 |
| HEIC／HEIF、JPEG XL 等扩展格式 | 后端包含相应编解码器时启用，缺失时报告能力缺失和安装方法 |
| SVG、PSD、相机 RAW 等 | 按后端能力作为输入；栅格化、合成图或显影是显式转换，不声称保留矢量、图层或传感器数据 |
| APNG、动图 GIF／WebP、多页 TIFF、多尺寸 ICO | 首版识别其结构，拒绝不受支持的完整压缩／转换；允许用户显式选取帧、页或尺寸后转换为静态图片 |

完整动画／多页保留是后续交付阶段，不能在完成前宣称支持这些格式的所有内容。其验收须覆盖帧数、时序、循环、混合／处置语义、页面信息和最终渲染结果。

上述阶段划分是建议，需要随本文一并确认；若动画或某种扩展格式必须首版支持，应在实施计划前调整范围。

## 4. 技术方案建议

使用 Rust 构建统一 CLI，暂定命令名 `ctk`。图片功能放在 `image` 子命令下，后续工具作为同级模块加入。选择 Rust 是为了直接使用 PNG 优化与解码库，并交付原生可执行程序。

- CLI：使用 clap 解析参数，业务逻辑与终端输出分离。
- PNG：内置 OxiPNG 库，使用其不同过滤、无损表示变换和压缩配置生成候选。
- 补充 PNG 引擎：通过适配器调用可用的 ZopfliPNG，以增加候选覆盖范围。它是可选增强依赖，缺失时须在报告中标明。
- 广泛格式转换：使用 ImageMagick 7 作为后端，运行时探测格式读写能力。PNG 核心路径无需安装 ImageMagick，通用转换需要安装后端及对应编解码器。
- 图片验证：使用独立于优化调用路径的解码与结构检查；PNG 比较原始精度的逻辑像素及显示相关信息。

首版采用“原生 CLI + 按需安装扩展后端”的发布方式，不承诺一个小型二进制包含全部编解码器。文档列出三种系统的安装方法，工具提供后端状态和缺失能力诊断。

本地环境检查结果：当前可发现 Python 3 和 ImageMagick，未在 PATH 发现 Rust 工具链；开始实现前需要准备 Rust。当前项目目录无现有代码、构建约定或 Git 仓库可继承。

建议首批发布平台：macOS arm64／x86_64、Linux x86_64／arm64（glibc）、Windows x86_64。Windows arm64 与 Linux musl 留作后续扩展；三系统分别构建和验证，不能把 macOS 本地通过当作三平台验证完成。

## 5. PNG 优化路线

### 第一层：得到可靠且可比较的结果

1. 检查文件真实格式、PNG 结构、尺寸、精度、动画状态及解码资源需求。
2. 将原文件加入候选集，作为大小和保真度的保底结果。
3. 对同一输入运行一组明确、有限、可复现的 OxiPNG 配置；不能假定最高优化级别或 Zopfli 在每张图上最小。
4. 补充引擎存在时生成更多候选；显式禁用改色和有损降位深，统一元数据策略。
5. 对每个候选验证格式有效性、像素与精度一致性、显示相关信息及要求保留的元数据。
6. 从全部合格候选中选择字节数最小者；候选相同时采用确定的优先级。
7. 通过临时文件完整写出，再发布到目标位置；异常和中断不得损坏原文件。

默认建议使用 `max` 档，以体积优先，运行有限候选集合；另提供更快的 `fast` 档。`max` 的含义是当前预设中搜索最充分，不是数学意义上的全局最优。

提供并发数、内存预算和时间预算设置。未指定时间预算时仍须在有限策略执行完后结束；指定预算后保存已完成且合格的最小结果，同时报告搜索是否完整。大图预先检查预计解码内存，超预算时给出明确错误。

### 第二层：尝试获得实际超越

在第一层结果可复现后，针对基准中仍有空间的图片研究调色板重排、扫描行过滤搜索和编码表示选择。所有优化都必须满足同一无损验证器。

不能把“调用多个现有工具取最小值”描述为已经研发出更强的压缩算法。需要区分：相对某个单一工具的收益，以及相对所有基线逐图最小结果的新增收益。

不能承诺任意 PNG 都会缩小，或每张图都严格小于所有现有工具。已经充分优化或难压缩的输入可能只能持平。总体优势是实验目标；若未达到，报告实际数据并保留为未完成的性能目标。

## 6. 拟定命令与文件行为

以下为设计时拟定的接口；当前可用命令以 README 和 `--help` 为准：

```text
ctk image compress input.png --output output.png
ctk image compress ./images --recursive --output-dir ./optimized --effort max
ctk image convert input.png --to webp --lossless --output output.webp
ctk image convert input.png --to jpeg --allow-lossy --quality 92 --background white --output output.jpg
ctk image info input.png
ctk image formats
ctk image doctor
ctk image benchmark ./corpus --output ./report.json
```

- `compress` 首版的专项优化保证针对静态 PNG；其他格式通过 `convert` 选择目标编码，不能误报为 PNG 同等级的专项优化。
- 默认保留输入文件；单文件压缩省略输出位置时生成 `name.optimized.png`，转换生成带目标扩展名的相邻文件。同格式转换必须显式给输出位置。
- 输出已存在时默认失败；覆盖已有输出需 `--overwrite`，替换输入需独立的 `--in-place`。两者的关系在实施计划中明确。
- 批量处理保留相对目录结构，预先检测同名冲突。默认不跟随目录符号链接，避免循环遍历。
- 单文件失败不阻止其他独立文件处理；结束时汇总失败，存在失败则返回非零退出码。
- 普通输出显示原大小、新大小、节省字节及比例、耗时、实际使用的引擎、是否完成搜索和验证结果。
- `--json` 输出结构化结果，诊断与进度写 stderr，便于脚本调用。
- 后端通过参数数组启动，不拼接 shell 命令；正确处理中文、空格、Unicode 和以短横线开头的路径。

## 7. 比较方法与验收

### 正确性

覆盖 RGB、RGBA、灰度、调色板、低位深、16-bit、透明隐藏 RGB、ICC／gamma、隔行 PNG、极小图片、损坏文件、超大尺寸声明、已有充分优化的输入，以及应明确拒绝的动画／多页输入。

无损 PNG 的验收为：独立解码成功、按原精度比较所有逻辑像素、检查要求保留的显示与元数据语义，且输出字节数不大于原文件。不得只做截图目测或将两边都转为 8-bit 比较。

格式转换的测试覆盖真实读写能力、透明度与精度限制、明确有损参数和不支持的结构；后端缺失应返回可操作的错误。三系统分别检查路径、进程调用、输出冲突和原子发布。

### 压缩效果

使用版本固定且具备使用权限的公开样本与合成样本，包含 UI 图标、截图、插画、照片、渐变、噪声、透明图、16-bit 图以及经过其他工具优化的输入。人工挑选的有利样本不得单独代表总体结果。用户后续可添加自己的素材作为单独的真实业务集合。

基线至少包括 OxiPNG 高档的常规压缩、OxiPNG 的 Zopfli 配置、ZopfliPNG 高搜索配置。锁定工具版本、完整参数、运行环境、元数据策略和无损约束；基线输出同样经过验证，不合格结果不参与压缩率排行。

报告数据：

- 总输入字节、总输出字节、总节省比例。
- 每张图的结果、相对各基线的差值、胜／平／负数量。
- 相对逐图最小基线的新增收益。
- 总耗时、单图耗时分布、峰值内存、预算未完成项。
- 元数据清理造成的变化，和重编码带来的变化分别说明。

比较同时给出“体积优先”和“相近时间预算”的结果，避免把大量额外计算造成的收益隐藏起来。当前未运行任何这样的基准，不能填写或宣传预计提升百分比。

功能首版和性能目标分别验收：功能首版要求上述安全输出、无损保证、格式能力报告和跨平台行为成立；“优于现有工具”必须在基准中取得证据后才标记达成，不能因功能完成自动判定达成。

## 8. 可由实施者决定的细节

具体依赖版本、模块与 trait 划分、有限搜索预设、资源预算默认值、测试框架、基准样本下载与许可记录方式，可在实施计划中根据 API 和环境确定。选择不得降低已确认的质量底线或暗中缩小格式范围。实现前先形成可审阅的实施计划；提交代码仍需用户另行确认。

## 9. 调研依据

- [W3C PNG 第三版规范](https://www.w3.org/TR/png-3/)：PNG 为无损光栅图格式，支持不同样本精度、颜色空间信息和动画。
- [OxiPNG 官方文档](https://github.com/oxipng/oxipng)：可作为 Rust 库使用；更高等级或 Zopfli 并非对每张图都更小；透明区改色属于有损变换。
- [OxiPNG 参数手册](https://github.com/oxipng/oxipng/blob/master/MANUAL.txt)：优化、元数据、透明度及压缩策略参数。
- [ZopfliPNG 官方说明](https://github.com/google/zopfli/blob/master/README.zopflipng)：多种过滤策略、无损表示选择及保留附加块的注意事项。
- [pngquant 官方说明](https://pngquant.org/)：它是有损量化压缩工具，不能直接作为严格无损目标的同质量基线。
- [ImageMagick 格式表](https://imagemagick.org/formats/)：不同格式的读取、写入、后端依赖与平台限制。
